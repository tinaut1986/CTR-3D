# Handoff 2026-11-11: Old 3DS race stalls

Branch `perf/o3ds-race-stalls` (cut from `release/v0.2.3`, local, not pushed): two commits, 7a57869 and dabb84a.
Measured on the Old 2DS in an Arcade race on Crash Cove (the owner drives, nobody polls FTP meanwhile).

## Baseline (v0.2.2 debug build, before this branch)

`[PACE]` race windows: work 35-38 ms a frame against the 33.3 ms of 30 fps, 6-20 skipped draws per 64 frames,
and stalls of 0.15-1.5 s. Split: OT walk 10.7 ms (empty slots ~2.6), end scene 6.3, instances 4.2, level geometry
4.2 (sky 2.3), splits 2.2, game logic ~2.5.

## Done

- XA music read-ahead on a background I/O thread (`n3ds_iothread.c`, disc owner `PREFETCH` with its own fd):
  the 64-sector span reads (~20-28 ms each) left the game thread.
- `N3DS_FlushDcache`: svcFlushProcessDataCache on the calling core instead of the GSP IPC; Old-3DS class
  defaults to `c3dflush 1`. End scene 6.3 -> 4.7 ms.
- Track mesh and atlas built at the end of the level load (`LOAD_TenStages.c`) instead of the first race frame
  (0.5-0.8 s freeze in the race intro).
- `[BEAT] THAW` no longer starts 10 s of synchronous SD flushes after any 500 ms gap (only >5 s system freezes):
  each was a 0.1-1.5 s stall, so one slow frame cascaded.
- OT empty-slot run: cached token range + per-stretch capture marks, ~600 -> ~145 cycles a slot.
- `deepprof` dumpreq (default off): [INSTPROF]/[GTEPROF]/[PARSEPROF] sampling. The production build was clearly
  faster than the debug one on the 2DS; with deepprof off the debug build is still slower than production
  (owner's report), so more of CTR_INTERNAL costs something.

## Tried and dropped

Render worker on core 1 (`core1.txt` / cfg `core1`, off by default; rsf MaxCpu back to 30 %). At 80 % the worker
kept up, but GSP and the other services on core 1 starved: C3D_FrameEnd 0.2 -> 5-7 ms, GPU 7 -> 15 ms a frame,
core 0 slower on shared memory. A real race ran no faster.

## State now (debug build, deepprof off)

Owner: production build "better, dips to 22 fps in places". Debug windows: 28-40 ms; heavy ones: OT walk 8-9 ms
(parse 6-7), instances 6.5-7, end scene 5.8-6 (track leaves 2.9-3.6), level geometry 4 (sky 2.2), splits 2.2,
queue instances 2.0.

## Next, in order

1. Instances (6-12 ms with many karts): the gate still decodes and projects every vertex on the CPU to choose
   the triangles the GPU draws.
2. Track draw issue cost (2.5-3.6 ms of CPU): per-leaf draws and depth uniforms.
3. Sky (2.2 ms): software-GTE projection of the dome every frame.
4. What else CTR_INTERNAL costs (debug slower than production with deepprof off).
5. Old-3DS texture cache: full-page decode bursts (20-50 ms frames) when the 7 atlases thrash.

## Update (later the same branch, 91f9513)

- `mdlfast` (default on): gated model triangles accepted in camera space (depth range + NCLIP sign from a
  determinant, strip FIFO of camera-space vertices); no projection, no screen window. In-race A/B said the
  projection was not the expensive part; models now total ~10-13 % of a race frame.
- OT walk links through a two-entry range cache.
- `sampler` dumpreq: the [SAMPLE] statistical profiler (1 ms samples of the game thread's location). Use it
  instead of [INSTPROF]/[PARSEPROF] phase splits, which are inflated by their own SVC tick reads.

Race profile now (debug build, [SAMPLE], work 28-36 ms): walk.parse ~9 %, track draw 3-10 %, sky ~6.5 %,
draw_all_splits ~6 %, end scene ~5.5 %, mdl.accept ~4-5 %, game logic ~5 %, walk.link ~4.5 %, walk.demit ~4.5 %,
texresolve 3-12 % (cache-miss bursts), track anim ~4 %. Post-race windows: confetti (an unmarked effects scope) ~11 %.

Next: sky on the GPU (or cached), track draw/end-scene issue cost, packet parse, texture-cache misses.
