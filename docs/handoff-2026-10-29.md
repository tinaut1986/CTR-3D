## In release/v0.1.0 (verified on a real New 3DS)

- Bottom screen owned by one writer, graphics mode from the first frame, tabs
  STATUS / MAP / OPTIONS / UPDATER / DEBUG (debug builds). Before, libctru's
  console (RGB565, single buffer), a CPU painter assuming BGR8, the map's
  display transfer and log prints all wrote the same framebuffer.
- CIA is the way to run it. `package-cia.sh` never passed `APP_SYSTEM_MODE_EXT`
  to makerom (env var instead of `-D`), so every CIA had run in the 64 MB legacy
  mode. Now SystemModeExt **124MB** (178MB made the return to HOME much slower).
- Own `__system_allocateHeaps` (`platform/n3ds/n3ds_heap.c`): a CIA gets only
  32 MiB of linear heap from libctru's default, which starved citro3d init.
- In-game FTP (port 5000): debug builds always on (toggle in DEBUG), production
  only with `dev-ftp.txt` (install-only). `./build3ds.sh --install <ip>` uploads
  + `SITE INSTALL` + relaunch. Verified many times.
- Clean exit (FTP joined, ndsp reset, citro3d synced) and **HOME -> Close no
  longer hangs** (APT suspend drain, timed joins, teardown on a thread; copied
  from sm-3ds 9aaf03c). Verified.
- Versioning (`platform/n3ds/tools/version.sh`, `CTR_VERSION`/`CTR3D_VERSION`
  override), in-game updater (curl + mbedTLS against GitHub releases, STABLE /
  + BETAS), release CI copied from zelda-tmc-3ds (betas carry the debug tools).
  **The updater has never run against a real release.**

## In feat/o3ds-support only (not yet in release)

Memory (Old 3DS): one CIA for both consoles, SystemMode 80MB on Old 3DS; lean
split linear 32 MiB / heap ~30 MiB; decode atlases 7 instead of 11 on small
linear; hw-voice store 2 MiB; no right-eye target on 2DS; clear fatal screens on
out-of-memory; FTP/updater on core 0 (priority 0x3F) without cores 2/3.
**Verified** in the Old-3DS simulation CIA: boots, fits, FTP works.

CPU (Old 3DS), each with host parity tests (`platform/n3ds/tests/perf-parity/run.sh`):
audio fallback runs the worker's job instead of the full software mixer
(~20 -> ~0.5 ms, verified); OT walk fast paths (~24 -> 4 ms in the menu,
verified); specialised software GTE ops; GPU-model "gate" (no software GTE for
claimed triangles); menu-flag lean projection and per-quad stereo depth;
visible-only track water animation; voice cache filled in the background and
stopped once full; async SD log writer; bottom STATUS repaint 1 s on Old 3DS.

Frame pacing: OPTIONS > FRAME SKIP = AUTO (default, 60/30/20 adaptive) / OFF
(60 whenever it fits) / 30 (retail). 3D EFFECT gains AUTO on Old 3DS.
**60 fps mode** (runtime port of CTR-ModSDK's USE_60FPS, `include/ctr_fps60.h`,
`game/MAIN/MainFps60.c`): karts/AI/camera/HUD at 60, weapons/particles/ghosts
at 30. **Never tested on hardware**; at 30 the code is the original.

Simulation: `./build3ds.sh --o3ds-sim` builds `ctr3d-o3dssim.cia` (own title ID
0x5A2C4, Legacy + 80MB, 268 MHz, no L2), the real Old-3DS memory mode on a New
3DS. `o3ds-sim.txt` in the data dir only fakes the heap side (not linear).
